# 通用软件发布规格（Release Spec）

> 适用于桌面 App、命令行工具、Web 站点与库的正式发布。目标：**同一个版本号，在任何地方看到的都是同一份东西**；发布可复现、可验证、可回滚、可追溯。
>
> TokenPeek 的具体落地步骤见 `docs/发布规则与问题.md`（本文只讲通用规则）。

## 1. 五条基本原则

1. **单一事实来源**：版本号只在一个地方维护（源码里的版本文件 / `package.json` / `Info.plist`），其它位置（站点、文档、Release 标题）都由它派生或校验，不手抄。
2. **发布不可变**：已经发布的版本号、tag、安装包不再修改。要改就发新版本。
3. **可验证**：每个产物都有 SHA-256；下载地址可访问；安装后的版本号与发布版本一致。
4. **可回滚**：保留上一个可用版本；出问题能撤回 / 标记 / 发补丁，不需要用户手动降级。
5. **可追溯**：任意一个安装包都能追到「哪个 tag → 哪个提交 → 哪次构建 → 哪份更新说明」。

## 2. 版本号规范

| 类型 | 规则 | 示例 |
|---|---|---|
| 语义化版本 | `MAJOR.MINOR.PATCH`，数字段不带前导零 | `1.8.0`、`2.0.1` |
| 预发布 | `-alpha.1` / `-beta.2` / `-rc.1` | `2.0.0-rc.1` |
| 构建号 | 单调递增整数，每次构建 +1，不复用 | `9`、`10` |
| 桌面 App | `CFBundleShortVersionString` 用 2–3 段纯数字；`CFBundleVersion` 为递增整数 | `1.8` / `9` |

硬性要求：

- **不允许** `1.6.01` 这类带前导零的三段写法：版本比较、自动加版、商店审核都可能出错
- **不允许**复用已发布过的版本号（哪怕内容不同）
- 发版前确认：源码版本、构建产物版本、Release 标题、站点显示版本、更新检查读取的版本 **五处一致**
- `MAJOR` 变更 = 不兼容；`MINOR` = 功能；`PATCH` = 修复。不要用版本号表达营销含义
- 自动加版脚本只能有一个入口；重复执行必须幂等（或用显式参数跳过）

## 3. 发布前检查清单

- [ ] 代码已合并到发布分支，工作区干净，CI 全绿
- [ ] 版本号已按第 2 节更新，且只有一处手动修改
- [ ] 依赖锁定（lockfile 已提交），构建环境固定（SDK / Node / Xcode 版本）
- [ ] 关键路径测试通过：单元测试 + 冒烟测试 + 至少一次真实安装
- [ ] 更新说明已写好并经确认（见第 6 节）
- [ ] 产物在干净目录构建（`rm -rf build` 后重编），不依赖上次残留
- [ ] 没有把密钥、证书、token、内部地址打进产物或仓库
- [ ] 上一版安装包仍可下载（用于回滚与对比）
- [ ] 站点 / 文档里没有残留旧版本号

## 4. 产物规范

**命名**

```
<产品>-<版本>-<平台>-<架构>.<扩展名>
TokenPeek-1.8-AppleSilicon.dmg
TokenPeek-1.8-Intel.zip
mytool_1.8.0_linux_amd64.tar.gz
```

- 只用 ASCII：字母、数字、`-`、`_`、`.`；**不要中文、空格、括号**
- 平台 / 架构必须写清（AppleSilicon、Intel、arm64、x86_64、universal）
- 同一版本的不同包使用同一种命名风格

**必须提供**

- 每个产物的 SHA-256（可另附 `SHA256SUMS` 文件）
- 安装 / 升级说明（尤其是签名、权限、最低系统版本）
- 许可证与第三方声明（如适用）
- 可选的构建信息：提交号、构建时间、工具链版本

**大小与渠道**

- 先确认分发渠道的单文件上限（GitHub Pages 约 100 MB、静态托管常见 25–100 MB、商店另有规则）
- 超出上限的包放 Release / 对象存储 / CDN，页面只放跳转链接
- 下载目录不要提交进仓库，也不要随站点全量部署

## 5. 签名、公证与信任

- macOS：`codesign` 签名；对外分发建议 notarize + staple。ad-hoc 签名必须明确告知用户「右键 → 打开」
- Windows：代码签名证书；没有签名要在说明里写清 SmartScreen 处理方式
- Linux：提供校验和与签名（GPG）可选
- **签名发生在打包最后一步**；修改包内任何文件（包括 `Info.plist`）后必须重新签名
- 签名 / 公证失败时不要发布，先修复；不要用「让用户关掉安全设置」掩盖问题

## 6. 更新说明（Release Notes）规范

**面向用户，不面向开发者。**

结构建议：

```markdown
- 新增：……
- 改进：……
- 修复：……
- 已知问题：……

下载：
- 平台 A（最低系统）：文件名
- 平台 B（最低系统）：文件名

安装说明：签名状态、首次打开方式、校验方法
```

规则：

- 每条一句话，动词开头，说「用户感知到什么」，不写内部函数名 / 工单号 / 提交号
- 数量控制在 3–6 条；重大变更单独说明升级注意事项与数据兼容性
- 不写未完成的功能，不承诺没有验证过的行为
- 不泄露内部信息：服务器地址、密钥、未公开计划、用户数据
- 结构化字段（版本、日期、下载列表、校验值）由脚本生成，避免手抄出错
- 内部 changelog 与用户更新说明分开维护

## 7. Tag 与提交规则

- tag 名与版本一一对应：`v1.8.0`（或团队约定的固定格式）
- tag 必须指向**已经合并、已经测试**的提交
- 已发布的 tag 视为不可变；必须修正时只能：删 Release → 重打 tag → 明确告知（尽量用新版本代替）
- tag 建议 annotated / signed：`git tag -a v1.8.0 -m "Release 1.8.0"`
- 发布记录要能回答：这个 tag → 哪个 commit → 哪个 CI 构建 → 哪些产物

## 8. 发布流程（标准流水线）

```
冻结 → 升版本 → 干净构建 → 签名 → 冒烟测试 → 生成校验和 → 打 tag
→ 建 Release（草稿）→ 审核更新说明 → 发布
→ 更新站点/更新源元数据 → 部署 → 线上验证 → 公告
```

要点：

- **草稿先行**：Release 先建草稿，检查资产 / 说明 / tag 后再点发布
- **先测后发**：至少在一台干净机器上安装并启动一次
- **先发布后改站点**：站点指向的下载地址必须已经可用
- **部署分离**：先 staging / 预览环境验证，再切生产
- **一次只发一个版本**：避免同一时间两个发布流程并行

## 9. 站点 / 更新源规则

- 站点上的版本号、下载文件名、校验值、更新日志，必须从同一份发布元数据生成；做不到时，发布后立即全局搜索旧版本号
- 下载链接使用**版本化地址**（`/releases/download/v1.8/...`），不要指向 `latest` 的固定文件名，避免新旧混用
- 静态资源加缓存破坏参数验证（`?v=<时间戳>`），确认线上真的更新
- 部署前先看目标分支最新提交，避免用本地旧副本覆盖别人的改动；`rsync --delete` 要谨慎
- 站点只放页面和小资源；大安装包放 Release / CDN

## 10. 更新检查与兼容性

- 更新检查比较版本号时要按数字分段比较，不要按字符串比较
- 明确更新渠道：稳定版 / beta 版分开，避免测试版推给所有用户
- 升级不能破坏用户数据：数据目录、配置键、文件格式变更要向前兼容或提供迁移
- 回滚时用户数据也要能回退，或至少不崩溃

## 11. 发布后验证清单

- [ ] Release 页面可访问，标题 / tag / 说明正确
- [ ] 所有资产存在，文件名与站点记录一致，大小合理
- [ ] 每个下载链接返回 200（跟随重定向后）
- [ ] 下载包 SHA-256 与公布值一致
- [ ] 安装后 App 内显示的版本号 = 发布版本
- [ ] 旧版本能检测到更新，且更新后的版本号正确
- [ ] 官网 / 文档 / 更新日志显示新版本，无旧版本残留
- [ ] 移动端 / 不同网络环境下页面可用（如适用）
- [ ] 回滚路径可用：上一版仍在，下载地址未失效

## 12. 回滚与故障处理

| 情况 | 处理 |
|---|---|
| 说明文案错误 | 直接改 Release 说明（不算新版本） |
| 某个平台包有问题 | 删除该资产并说明；其它平台保留；尽快发补丁版 |
| 版本整体不可用 | 把 Release 标记为 pre-release / 撤下，恢复上一版为 latest；发新 PATCH 版 |
| 站点部署出错 | 回滚到上一个部署提交，确认线上恢复后再排查 |
| 更新推送错误 | 立即停止更新源指向，修正元数据；必要时发「回退版」 |
| 数据被破坏 | 提供迁移/修复工具，暂停自动更新，发布说明中明确告知 |

规则：

- 已发布的安装包**不要悄悄替换**（校验和会变，用户无法追溯）
- 回滚必须验证：旧版本能装、能启动、能读到已有数据
- 每次事故记录：现象、影响范围、根因、修复、如何避免

## 13. 安全与合规

- 不在仓库、构建日志、产物、Release 说明中出现密钥 / token / 证书 / 内网地址
- 构建使用最小权限的 CI 凭据；签名密钥单独保管
- 第三方依赖做许可证检查；升级依赖要跑完整测试
- 用户数据处理符合隐私政策；遥测默认关闭或明确告知
- 下载页提供校验值，重要发布可提供签名文件

## 14. 常见发布问题库

### 14.1 版本号漂移
- 症状：App、Release、站点显示的版本不一致
- 原因：版本号多处手写、只改了一部分
- 处理：统一来源；发布后全局搜索旧版本号；把版本校验加入发布脚本

### 14.2 重复升版 / 版本跳号
- 症状：重打一次包，版本又 +1
- 原因：自动加版脚本不幂等
- 处理：提供「跳过升版」参数；打同版前先确认当前版本

### 14.3 版本号格式非法
- 症状：自动加版算出 `1.0`、商店拒绝、更新检查异常
- 原因：三段式带前导零或非数字段
- 处理：严格两段或三段纯数字；脚本里加格式校验并在发布前失败

### 14.4 资产缺失 / 命名不一致
- 症状：页面 404、下载按钮指向不存在的文件
- 原因：构建失败未发现、大小写不一致、版本号拼接错误
- 处理：发布前用脚本比对「产物目录 ↔ 元数据 ↔ Release 资产」三份清单

### 14.5 下载 404
- 症状：链接打不开
- 原因：tag 未推送、Release 未发布、资产名不匹配、base URL 写错
- 处理：先查 Release 资产列表，再查元数据里的文件名与 base

### 14.6 站点没更新（缓存 / 手动文案）
- 症状：数据文件更新了，页面还是旧的
- 原因：CDN / 浏览器缓存；页面版本号是手写的
- 处理：cache-buster 验证；把版本号改为脚本注入；发布后逐处检查

### 14.7 覆盖部署
- 症状：刚发布的站点内容被旧副本覆盖，或别人的改动消失
- 原因：`rsync --delete` / 强制推送 / 复用旧工作目录
- 处理：部署前拉取最新分支并对比；禁止对主分支强推；部署后验证关键页面

### 14.8 并发发布
- 症状：push 被拒、历史里出现意外提交、两个版本交叉
- 处理：发布加锁（同一时间只允许一个发布）；提交前 `git status` / `git log`；保留他人提交

### 14.9 tag 与提交不一致
- 症状：Release 指向的源码不是实际发布的代码
- 原因：先打包后提交、tag 打在旧提交、移动过 tag
- 处理：先提交再打 tag；发布前核对 `tag → commit`；已发布 tag 不改

### 14.10 签名 / 公证问题
- 症状：用户打不开、系统提示「已损坏」
- 原因：未签名、签名后改了包内容、未公证、证书过期
- 处理：签名放最后；发布前在干净机器验证；文档写清打开方式

### 14.11 架构 / 最低系统版本错误
- 症状：在目标机器上无法启动
- 原因：构建目标架构不对、最低系统版本高于用户系统
- 处理：分别构建各架构；检查产物架构与最低版本；在最低版本系统上实测

### 14.12 更新检查失效
- 症状：旧版本收不到更新，或误报新版本
- 原因：字符串比较版本、地址写死旧仓库、渠道混用
- 处理：数字分段比较；更新地址可配置；稳定版 / 测试版分渠道

### 14.13 发布说明泄露内部信息
- 症状：说明里出现内部地址、密钥、未公开计划
- 处理：发布说明只写用户可感知的变化；敏感信息走内部文档；发布前人工过一遍

### 14.14 回滚不彻底
- 症状：撤下新版后，用户仍被推送到坏版本，或旧版装不回
- 原因：更新元数据未改、旧版资产被删、数据格式已升级
- 处理：保留上一版资产与数据兼容；回滚时同步更新元数据；回滚后实测

### 14.15 校验和不匹配
- 症状：用户校验失败
- 原因：公布值来自旧构建、上传了另一个文件、传输损坏
- 处理：校验和与产物同一次构建生成；发布前重新计算比对

## 15. 建议的自动化（可选）

一条最小流水线：

1. `lint` + `test`
2. 读取版本（唯一来源）→ 校验格式
3. 各平台构建 → 签名 → 产物清单 + SHA-256
4. 冒烟测试（安装 / 启动 / `--version`）
5. 打 tag → 创建 Release 草稿并上传资产
6. 生成站点元数据（版本、下载列表、更新日志）
7. 部署预览 → 自动检查 200 / 版本号 / 校验值 → 切生产
8. 通知（邮件 / webhook）

任何一步失败都应中断发布，不允许「先发出去再补」。
